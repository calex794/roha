# СТАЯ — проверенные пробелы Roha/noq по результатам аудита форков

Дата: 2026-10-19. Источники: основные ветки [calex794/roha](https://github.com/calex794/roha) и [calex794/noq](https://github.com/calex794/noq), а также перечисленные конкретные патчи. Ничего из чужих форков ещё не внедрено.

## P0: ROHA-NOQ-PATH-BACKPRESSURE — независимая перегрузка сетевых путей

**Подтверждённый текущий код.** `roha/iroh/src/socket/transports.rs`, реализация `Sender::poll_send` около строк 1277–1305: результат `Poll::Pending` от отправителя конкретного пути заменяется на `Poll::Ready(Ok(()))` с сообщением о потере пакета. Случай переполнения очереди `RemoteStateActor` около строк 1190–1218 аналогично обрабатывается без гарантированного сохранения пакета — отдельная граница проблемы. `noq/noq/src/connection.rs`, `drive_transmit` около строки 1667, сохраняет один `buffered_transmit` при `Poll::Pending` и останавливает общий проход до пробуждения. Поэтому простое возвращение `Poll::Pending` из Roha блокирует отправку также по свободным путям.

**Кандидат:** [HeddleCo b7bc6c3](https://github.com/HeddleCo/iroh/commit/b7bc6c34983ebac2b613d0184e6a9ce19fc47c38) — `WouldBlock` и независимое ожидание конкретного пути. Однако патч использует абсолютные локальные `/Users/lukethorne/dev/HeddleCo/noq/...` в Cargo.toml. Без адаптации к **нашим** Roha/noq и воспроизводимой фиксации версий использовать нельзя.

**Приёмка**:
1. Путь A блокируется; свободный B продолжает отправлять в том же соединении.
2. A не теряет непосланный пакет и продолжает передачу после готовности.
3. Закрытие A или соединения корректно снимает ожидание без вечной блокировки.
4. Очередь по каждому пути имеет ограничения памяти и справедливое обслуживание.
5. Отдельно проверить переполнение очереди RemoteStateActor, прямой IP, relay и пользовательские транспорты.
6. Тесты проходят как в нашем noq, так и в нашем Roha; Cargo.lock воспроизводим, абсолютных локальных путей нет.

Статус: подтверждённая проблема, решение **не реализовано**.

## P0: RELAY-HOST-CHALLENGE — привязка подписи к конкретному посреднику

**Подтверждённый текущий код.** `roha/iroh-relay/src/protos/handshake.rs`: `ServerChallenge::message_to_sign` около строк 210–220 вычисляет `blake3::derive_key(DOMAIN_SEP_CHALLENGE, &self.challenge)` только по вызову. Проверка и подпись (около строк 229 и 236) не добавляют идентификатор relay. Более быстрый путь TLS exporter существует отдельно, но не всегда применим, особенно в браузере/за TLS-терминатором.

**Кандидат:** [bxff 1af5a05](https://github.com/bxff/iroh/commit/1af5a056dd0e3429fb34e21ea363fa9962ceb496) — привязка вызова к `RelayUrl` на обеих сторонах (включая изменение API `RelayService::new`, `serverside`, `RelayConfig`). Сам автор описывает неизменность формата передачи, но **проверки совместимости старых и новых клиентов ещё нет**. Не переносить слепо.

**Приёмка**:
1. Подпись для relay A отвергается при попытке использовать её для relay B с тем же вызовом.
2. Подпись для корректного relay A принимается.
3. Старые/новые клиенты и серверы: ясная политика несовместимости, никаких молчаливых ослаблений.
4. Покрыть HTTP и HTTPS, прокси, веб-среду, канонизацию имени, порт и IPv6.
5. Проверить авторизацию и обработку заголовков, не только один вызов `message_to_sign`.

Статус: текущий алгоритм не привязывает подпись к relay; применимость и безопасность адаптации требуют тестов.

## P1: LATE-RELAY-PATH — поздно полученный резервный маршрут

**Подтверждённый текущий код.** В `roha/iroh/src/socket/remote_map/remote_state.rs` (примерно строки 430–446) известные relay-адреса открываются в только что добавленном соединении при выигрыше IP. Поздние события изменения адресов (строки ~285–289) в основном вызывают попытку NAT-пробивания, не гарантируя открытия резервного relay-пути уже живому соединению. `roha/iroh/src/endpoint.rs` (строки ~1117–1145): адреса обычно передаются через `connect_with_opts`.

**Кандидат:** [agent-habilis 0e7cdb4](https://github.com/agent-habilis/iroh/commit/0e7cdb4cd73952c49699cd7ae971a1fc2982b866), в сочетании с предыдущим API-коммитом о добавлении адресов без нового соединения.

**Приёмка**: сначала прямой путь и передача данных; затем появляется relay; затем прямой путь пропадает; та же сессия переключается на relay. Зафиксировать дополнительный keep-alive-трафик и квоты, не создавать бесконечное число резервных путей.

Статус: гипотеза о конкретном сценарии подтверждается существующими ветвлениями кода и патчем кандидата; тест отсутствует, исправление **не внедрено**.

## Как использовать эти находки

1. Сначала добавить независимые воспроизводимые регрессионные тесты в наши Roha/noq.
2. Сопоставить полный diff и историю оригинальных патчей с текущими версиями наших форков.
3. Адаптировать по смыслу, не копировать целые форки и случайные зависимости.
4. Запустить GitHub Actions, проверить блокировку маршрутов, fail-closed в безопасности, память и межплатформенную работу.
5. Сопоставить с массовым аудитом нормализованных патчей: [сценарий](https://github.com/calex794/roha/blob/lab/staya-iroh-fork-census-20261019/tools/staya/iroh_patch_audit.py), [запуск №39164490454](https://github.com/calex794/roha/actions/runs/39164490454). До завершения сравнения числа реальных независимых сетевых функций **не установлены**.
